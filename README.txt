FLOW LAB — NVIDIA RTX PRO 6000 EDITION

Open index.html in a modern browser. Keep all six app files in the same folder. No installation, account, internet, or real GPU is required.

Start with one illustrated machine and eight NVIDIA RTX PRO 6000 GPUs, each with 96 GB VRAM (768 GB across the fleet). Memory is local to each GPU, not automatically pooled. Add the inference app, JupyterHub, Langfuse, storage, and an online endpoint using the switches. Choose Linux, Docker, or Kubernetes.

Drag a model onto a GPU or click its card then a destination. A successful placement selects that model for NEW traffic. Existing requests keep their original model. Use “Send new requests to” to route to any catalog model. Click placed copies to inspect, move, remove, or open their official documentation.

Catalog: Qwen3-8B and 32B; gpt-oss-20b and 120b; Gemma 3 27B IT; DeepSeek-R1 Distill Qwen 32B and full R1; YOLO11s; BGE-M3 embedding; BGE reranker v2 M3. The task panel and Follow one request explain the different inputs and outputs. The mixed AI lab loads eight independent workloads. These are simulated requests, not actual AI results or a complete RAG pipeline.

Hardware capacity is real. All model reservations are illustrative estimates for the shown formats, including assumed working space. Actual VRAM depends on context, batching, runtime, caches, and sharding overhead. Full DeepSeek-R1 uses a hypothetical 720 GB FP8 reservation (90 GB on each of eight GPUs); this does not guarantee a real deployment fits. Processing rates are invented and are not benchmarks.

Sharing is enabled by default. Drop several models onto the same card, within its combined 96 GB teaching budget. Each model has a separate draggable label. Dedicated mode reserves each GPU for one workload. The five-model sharing preset uses 46 GB on GPU 1. Enable mixed traffic to see active workloads share compute; move a model to another GPU to give it separate compute. The lab checks memory estimates before placement, but real NVIDIA time-slicing does not isolate memory or enforce these GB limits. Sharing in Kubernetes assumes the administrator configured NVIDIA GPU sharing. Each distributed model group uses dedicated cards in this simulation. YOLO, embedding, and reranking copies each use one GPU regardless of the split lever. CPU support and online model hosting are conceptual, not runtime or provider compatibility claims. A distributed model requires serving software that supports its layout; Kubernetes does not split weights automatically. Automatic recovery is enabled in Kubernetes mode. It recreates CPU workloads and GPU model copies on suitable healthy resources; distributed workers assume a cooperating job controller. Unplaced recovery work stays Pending and retries.

Mint dots carry inputs; orange dots carry results; purple dots show model workers exchanging intermediate results; pink dots show application trace records or notebook data; blue pulses show deployment instructions. Sources are linked in the app and in each model inspector.

Kubernetes manages a fleet of GPU devices, not one automatic 768 GB VRAM address space. The eight-card summary shows free memory on each card and the largest free space on a single working card. Sharding a model requires compatible serving software and communication between cards.

PLATFORM LAYERS AND WORKLOAD MIX
Try Busy platform. Four illustrated user apps feed separate application queues and model-serving processes / containers / Pods, with bindings to the same physical workloads below. Queue cards represent waiting requests. Mix sliders set relative demand; the total traffic slider sets requests per simulated second. Each type targets a specific model, including when no copy is deployed. Changing a route affects new requests only. Chat rush and Camera rush deliberately overload a type. Every model has an 80-request buffer, with a 400-request overall cap.

Kubernetes mode adds a Request another replica action. The toy scheduler chooses suitable GPU resources; a request with no fit remains Pending and retries. Distributed copies need empty physical cards. Queue-based autoscaling is not automatic. In Linux and Docker modes, adding a copy asks you to choose its destination. The application queue and ready-copy dispatch are teaching conveniences, not features guaranteed by Kubernetes Services.

Langfuse shows simulated application traces with queue, compute, and total times. It observes requests but does not schedule them. Pink messages represent traces sent by application instrumentation. Click a waiting request card to follow it or a trace row to inspect timing. Multi-GPU logical groups summarize several worker Pods, with one worker container per GPU in this illustration. The hardware view repeats those same workloads; it is not a second deployment or a separate request hop.

REMOVING AND RESETTING
Use the visible × button beside each GPU model (or a model on CPU/online hardware) to remove that copy. Shared neighbors remain in place; deleting a distributed copy frees all its pieces. In-flight work for the removed copy goes back to its model queue. Reset lab clears all placements, traffic, queues, traces, pending replicas, optional layers, and counters, returning to eight empty 96 GB GPUs.

KV CACHE AND REQUEST TRACKING
The KV controls reserve extra memory for autoregressive language models: context (thousands of tokens) × slots per copy × adjustable GB per thousand tokens × precision factor. This is a generic teaching coefficient, not a model-specific sizing result. The fixed base reservation is treated as excluding this adjustable KV budget. GPU bars separate base memory from yellow KV reservation; the live-use line grows during processing. CPU copies use RAM for their cache; hosted copies do not use local memory. More slots allow concurrent requests but do not multiply GPU compute capacity. Changing KV settings restarts in-progress language requests. Over-budget copies stop serving until the plan fits.

Track one request opens a persistent six-layer guide. By default the entire simulation pauses at each stage; Next layer resumes until the next transition. Uncheck the pause option for continuous tracking. Show this layer scrolls to the highlighted UI, queue, container/Pod, GPU, response, or Langfuse dashboard. Requests on failed workloads return to the application queue and rebuild their temporary KV state after recovery. Node detection, loading weights, and distributed recovery are accelerated teaching shortcuts, not live migration.
